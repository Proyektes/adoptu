# adoptu: JVM vs GraalVM native-image throughput benchmark

Produced on a remote AWS EC2 box (8 vCPU / 15GB RAM, Amazon Linux 2023) per the constraint that
native-image builds must never run on the requester's local laptop. Raw wrk output and docker
stats for every rep are archived alongside the working copy of this report and are not committed
here; see the session record for exact paths.

This is the empirical data backing the Terraform decision already made on branch
`native-image-tuning`: the JVM runtime profile now kicks in at >=1 vCPU (1024 cpu units) AND
>=1GB memory instead of >=2 vCPU/2GB, because these are long-lived services where JIT warm-up
doesn't matter (see `AGENTS.md`'s "Runtime profile by task size" table and `infra/ecs.tf`).

## Matrix

Images: `adoptu:native` (GraalVM Oracle native-image, serial GC, `--no-fallback -O3
-march=x86-64-v3`, quickBuild), `adoptu:jvm` (Amazon Corretto 25-alpine).
Endpoints (see "Deviations" below for why these differ from the literal task wording):
`GET /health` (substitute for `GET /`) and `GET /api/pets?country=MEXICO`.
Load tool: `wrk` (built from source; `hey` is not packaged for Amazon Linux 2023). Concurrency
20, three 30s measured reps per (image, sizing, endpoint) after a uniform 60s warm-up hitting
`/api/pets?country=MEXICO`.

## Verdict

JVM overtook native image on raw throughput at **every sizing tested**, on both endpoints,
including the smallest (0.5 vCPU / 1024m) - not only at >=1 vCPU/1GB as the Terraform threshold
assumes. The gap widens with size: on `/health`, JVM leads by ~22% at 0.5 vCPU, ~26% at 1 vCPU,
and ~36% at 2 vCPU; on `/api/pets` (the DB-backed endpoint) JVM leads by ~11%, ~17%, and ~33%
respectively. This is consistent with the task's framing that JIT warm-up isn't the bottleneck
for a long-lived service given a fixed 60s warm-up window: HotSpot's C2 compiler produces more
aggressively profile-guided machine code than native-image's ahead-of-time compilation once fully
warm, even under fractional-vCPU contention.

That said, raw throughput is not the whole story, and the two runtimes trade off very differently
on the other axes the Terraform decision also has to account for:
- **RSS**: native stays flat at ~22-25MiB at rest (~90-96MiB peak under load) across all three
  sizings. JVM's footprint scales with the sizing's heap cap - 168MiB at rest at 0.5 vCPU/1GB
  growing to 294MiB at 2 vCPU/2GB - roughly 7-13x native's footprint at every size tested.
- **Startup time**: native starts in 114-219ms regardless of sizing. JVM startup is inversely
  proportional to CPU (more cores to JIT-warm the class-loading/init path faster): 8.5s at 0.5
  vCPU, 4.1s at 1 vCPU, 2.1s at 2 vCPU - 10-40x slower than native to first 200, though still
  fully acceptable for a long-lived ECS task that isn't scaling per-request.

Given the throughput numbers alone, the Terraform threshold could arguably be pushed lower than 1
vCPU/1GB. The 1 vCPU/1GB floor as chosen is a reasonable, conservative line given the memory
overhead (7-13x) and startup delay (10-40x) also documented here - both real costs on ECS Fargate
even when JIT warm-up itself isn't a user-facing concern for a long-lived task.

## Deviations from the literal task instructions (and why)

- **Endpoint paths**: the task named `GET /` and `GET /api/pets`. The backend has been JSON-API-
  only since a static-site migration - `GET /` 404s (confirmed both by curl against a running
  container and by `scripts/benchmark.sh`'s own comment: `"/" 404s here now`). Used `GET /health`
  instead, the script's own documented default substitute endpoint. Separately, `GET /api/pets`
  requires a `country` query parameter (`PetsRoutes.kt`) - it 400s with `{"error":"Country is
  required"}` otherwise. `scripts/test_data.sql`'s pets rows are all backfilled to
  `country='MEXICO'` (from `currency='MXN'`), so `GET /api/pets?country=MEXICO` is the endpoint
  that actually returns real, non-empty data (42 pets loaded).
- **JVM flags**: all of `-XX:+UseG1GC -Xmx<..>m -XX:MaxMetaspaceSize=96m
  -XX:ReservedCodeCacheSize=64m -XX:+UseCompactObjectHeaders` were accepted as-is by Amazon
  Corretto 25 with no `-XX:+UnlockExperimentalVMOptions` needed (`UseCompactObjectHeaders` is a
  GA feature in this JDK 25 build) - no flags dropped.
- **Native-image OOM workaround**: not needed. Peak RSS during the real compile was 10.42GB on
  the box's 15GB, comfortably under the limit once the real bugs below were fixed - the
  `-J-Xmx12g` build-arg contingency in the task brief was never invoked.
- **Load tool**: `hey` is not packaged for Amazon Linux 2023 (`dnf` has no match); built `wrk`
  from source instead (needed `perl-FindBin`/`perl-IPC-Cmd` beyond the task's listed
  `gcc git openssl-devel make`, since wrk's Makefile builds a vendored OpenSSL that needs them).
  `wrk --latency` gives the same p50/p99 percentile data `hey` would have, so no data-quality
  degradation.

### Two real bugs found and fixed (box-local only, never committed - see below)

1. **GraalVM toolchain resolution picked a broken downloaded JDK instead of the container's own
   working one.** `backend/build.gradle.kts`'s `graalvmNative` block requests
   `vendor.set(JvmVendorSpec.matching("GraalVM"))`. The Oracle GraalVM native-image:25 builder
   image's own JDK reports `java.vendor=Oracle Corporation` (the string "GraalVM" only appears in
   `java.vendor.version`), so that vendor spec never matches the working, native-image-capable JDK
   already in the container - Gradle silently fell back to auto-provisioning a
   `graalvm_community-25` toolchain via Foojay. On this box, that downloaded toolchain's
   `bin/native-image` came out as a 0-byte, non-executable file (mode 644), producing
   `java.io.IOException: ... Exec failed, error: 13 (Permission denied)`. Fix (box-local edit to
   `backend/build.gradle.kts`, reverted before commit): matched `JvmVendorSpec.matching("Oracle")`
   instead, combined with `-Dorg.gradle.java.installations.paths=$JAVA_HOME
   -Dorg.gradle.java.installations.auto-detect=false -Dorg.gradle.java.installations.auto-download=false`
   on the `Dockerfile`'s `nativeCompile` invocation, so Gradle uses the container's own toolchain
   and never attempts the broken download.
2. **The `jvm` Dockerfile stage's `java -jar` target has no runnable manifest.** The builder stage
   only ran `:backend:jar` (a thin jar, app classes only, no bundled dependencies or Main-Class
   manifest attribute) - `docker run adoptu:jvm` crash-looped immediately with
   `no main manifest attribute, in adoptu-backend.jar`. `scripts/benchmark.sh` already works around
   this for its own use case by building `:backend:shadowJar` instead. Fix (box-local edit to
   `Dockerfile`, reverted before commit): also run `:backend:shadowJar` in the builder stage and
   COPY the resulting `*-all.jar` (not `*.jar`) into the `jvm` stage. This is a genuine,
   previously-untested gap in the new `jvm` Dockerfile target (this Terraform branch is the first
   time a `>=1vCPU/1GB` task would ever have selected the `jvm` profile in production) - it should
   be fixed for real in a follow-up commit, not just worked around here.

Both fixes were applied only to the box-local copy of the repo under `~/adoptu` on the AWS
instance, confirmed working, and are **not** part of the commit made from the local checkout in
this task (see "Cleanup" below - the box's copy is left as-is per instructions, but nothing from
it was copied back into the local `/home/laf/Proyektes/adoptu` checkout other than this report).
