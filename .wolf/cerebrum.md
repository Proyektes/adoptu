## Key Learnings

- **Project:** adoptu
- **Description:** A Kotlin pet adoption web application with **FIDO2/WebAuthn** passwordless authentication. Multi-page application with HTML rendered from Kotlin (kotlinx.html).
- **Gradle multi-module:** Root `build.gradle.kts` uses `apply false` plugins + explicit `tasks.register("test")` delegating to `:backend:test` AND `:frontend:jsTest`. The root project never applies Kotlin directly.
- **Kotlin/JS yarn tasks:** `kotlin.js.yarn=false` in `gradle.properties` does NOT work in Kotlin 2.3.20 — yarn still runs (`kotlinYarnSetup`, `kotlinNpmInstall`). `KotlinNpmInstallTask` extends `DefaultTask` (not `Exec`), so `.environment()` is unavailable. The only way to inject `NODE_OPTIONS` is in `gradlew` before the JVM starts.
- **Node.js 22 + yarn 1.x:** DEP0169 (`url.parse()`) and DEP0040 (`punycode`) warnings come from yarn 1.22.17 internals. Fixed by exporting `NODE_OPTIONS="--no-deprecation"` in `gradlew`.
- **Frontend test task name:** Kotlin/JS with `js(IR)` target uses `jsTest` (not `test`) — the root test task must `dependsOn(":backend:test", ":frontend:jsTest")`.

- **i18n strings are duplicated in two places:** Each page's Kotlin (e.g. `SheltersPage.kt`) renders a hardcoded English fallback string with `attributes["data-i18n"] = "<key>"`, while `frontend/src/jsMain/kotlin/com/adoptu/frontend/I18n.kt` holds the same key translated across 5 locales (en, es, fr, pt, zh). Both must be updated together when correcting copy — editing only one leaves a stale fallback or stale translation.

- **DatabaseFactory.listOfTables must be kept in sync with Models.kt:** Every `Table` object defined in `Models.kt` must be added to `listOfTables` in `DatabaseFactory.kt` — omitting one means `SchemaUtils.create()` never creates that table, causing a PSQLException at runtime. Tables previously missing: `UserSterilizationLocations`, `UserShelters`, `PasswordResetTokens`, `EmailChangeTokens`.

- **`npx sass` fails in this sandbox** (`npm ERR! Cannot read properties of undefined (reading 'stdin')`). Use the vendored dart-sass binary directly instead: `.gradle/sass/1.54.0/dart-sass/sass backend/src/main/scss/<name>.scss backend/src/main/resources/static/css/<name>.css --no-source-map`. Only top-level `.scss` files (not `_partial.scss` files) compile to their own `.css` — check which top-level files `@use`/import a changed partial (e.g. `grep -l "<partial-name>" backend/src/main/scss/*.scss`) and recompile each of those too. (If the vendored binary is unavailable, see the `npm pack`-based fallback in Do-Not-Repeat below.)
- **`.pet-card` markup is duplicated across pages, not shared via a component:** `backend/src/main/resources/static/js/index.js` (home/browse page) and `my-pets.js` (My Pets page) both hand-build the same `.pet-card` HTML string against the shared `.pet-card`/`.pet-info`/`.pet-name` rules in `style.scss`. `index.js` is the more complete/correct reference implementation (it wraps age/rescue-date in `.label`/`.value` spans as the CSS expects). When fixing pet-card display bugs, check both files for the same divergence — a fix applied to only one page will leave the other inconsistent.
- **`Country` (backend/src/main/kotlin/com/adoptu/common/Country.kt) is the single source of truth for country values.** The dropdown (`Shared.kt: countrySelect()`), DB storage (`Models.kt` columns use `enumerationByName("country", 100, Country::class)`), and validation (every repository touching a `country` column calls `Country.fromDisplayName()` before reading/writing) all derive from this enum. DTOs stay `String` on the wire (`country: String`) — repositories parse at the boundary, throwing `IllegalArgumentException` on insert/update with an unrecognized value, and returning `emptyList()` on a search filter with an unrecognized value. `Country.fromDisplayName()` does accent/case-insensitive fallback matching, so stray input (e.g. `"México"` vs `"Mexico"`) still resolves instead of silently returning zero results.
- **Test fixtures must use real canonical country names from `Country.kt`, not placeholders.** Several test files used `"USA"` as a stand-in country value — it was never a real dropdown option (the canonical value is `"United States"`) and broke once country columns became enum-backed. Always use an exact `Country.entries` `displayName` in test data.
- **There are TWO parallel i18n systems and only one is live:** `frontend/src/jsMain/kotlin/com/adoptu/frontend/I18n.kt` (Kotlin, compiled into `common.js` via `:frontend:jsBrowserProductionWebpack`, exposed as `window.AdoptuI18n`) is what every page actually uses — `Shared.kt`'s `commonScripts()` wires `window.t` to it. The static files under `backend/src/main/resources/static/js/i18n/i18n-*.js` (plain JS, with their own `t()`/`i18n.translations`) are NOT loaded by any page (`Shared.kt` never adds a `<script>` tag for them) — they're dead code. Always add new translation keys to `I18n.kt`, never to `static/js/i18n/i18n-*.js`, and grep `t('keyName')` against `I18n.kt` (not the static i18n files) when chasing an "untranslated key shown literally" report.
- **After editing I18n.kt, rebuild the bundle:** `./gradlew :frontend:jsBrowserProductionWebpack` (task `:frontend:copyJsToBackendResources` then copies the output into `backend/src/main/resources/static/js/common.js`/`.js.map`). Editing the Kotlin source alone has zero effect until this runs.
- **`gradle/wrapper/gradle-wrapper.jar` is now tracked by git** (fixed 2026-06-30 — a `.gitignore` rule-order bug previously shadowed the negation that was supposed to un-ignore it; see Do-Not-Repeat). If `./gradlew` ever fails again with "Unable to access jarfile" in a fresh checkout, check `.gitignore` rule order before assuming it needs a manual copy.
- **EnterWorktree's default `fresh` baseRef branches from `origin/main`, which can be far behind local `main`** when prior sessions merged work locally without pushing. Before editing files that recent sessions touched (e.g. `I18n.kt`), diff the worktree branch against local main's HEAD; if stale, `git merge <local-main-sha>` into the worktree branch before starting work (or after, before merging back) to avoid silently reverting recent fixes.

- **The "previous deployment" referenced for infra work lives in AWS account `174000857825` (profile `adoptu` in `~/.aws/config`), not the CLI's `default` profile** (which resolves to an unrelated personal account, 716008900343, with no relevant permissions). When asked to prepare IaC "based on the previous deployment," always verify the AWS identity (`sts get-caller-identity`) actually matches before trusting README/buildspec account IDs — they can be stale.
- **The real adopt-u.org production stack was hand-built via the AWS Console (ECS "Express" deploy wizard, evidenced by the `ecsInfrastructureRoleForExpressServices` IAM role and auto-named `default-adoptu-*` security groups), with zero IaC and zero working CI/CD** — `buildspec.yml`'s CodeBuild/CodePipeline projects and Secrets Manager ARNs were never actually created in the account; it's a template that was never wired up. Don't trust buildspec.yml/README deploy docs as ground truth for what's actually running — verify against the live account.
- **Live prod had real bugs worth knowing about**: ECS task definition hardcoded `ADOPTU_DB_PASSWORD` in plaintext (same value as the documented dev default in AGENTS.md); the IAM task policy's S3 statement was scoped to a literal unfilled placeholder ARN (`your-bucket-name`); the container port mapping (80) didn't match what the app actually listens on (8080, per Dockerfile/application.conf). The apex/api domain resolving via a hand-entered DNS A/AAAA record pointing at one Fargate task's IP directly is an **intentional** design choice (no load balancer), not a bug to fix — see Do-Not-Repeat. There's also a stale `AAAA` alias to an `ecs-express-gateway-alb` that no longer exists - that's leftover from an earlier, abandoned attempt at a load-balanced design, evidence the no-LB choice was deliberate, not an oversight.
- **adopt-u's CloudFront app origin is `http-only` on port 8080 (no TLS to origin) by design, verified against the live distribution's actual `CustomOriginConfig`** — not a security gap to "fix" by adding a load balancer. Without an LB there's no AWS-managed TLS termination point in front of the app; encrypting that hop would require the Ktor container terminating TLS itself (Netty/Ktor SSL config + ACM Private CA, since plain ACM certs can't be installed on self-managed compute), which hasn't been requested. When asked to write IaC "matching the live deployment," check the actual running resource's config via the API before assuming a setting looks wrong (e.g. `aws cloudfront get-distribution`) rather than improving it unprompted.
- **RDS in a VPC with IPv6-only ECS subnets needs `network_type = "DUAL"`**, not just IPv4 — an IPv6-only Fargate task has no IPv4 address on its ENI at all, so it cannot open an IPv4 TCP connection to an IPv4-only RDS endpoint even though they're in the same VPC. The DB subnet group must support `DUAL` (check `aws rds describe-db-subnet-groups`) before this is possible; intra-VPC routing then handles it with no NAT/IGW involved either way.
- **For "no NAT" + IPv6-only ECS Fargate**: a VPC with an Amazon-provided IPv6 `/56` (the default for newer default VPCs) is "public" IPv6 — the VPC's main route table already has `::/0 -> igw`, so IPv6-only subnets get direct internet egress through the regular Internet Gateway with zero extra routing config (no NAT Gateway, no Egress-Only IGW needed). ALBs, however, still require a subnet with an IPv4 CIDR present (even when using `ip_address_type = "dualstack-without-public-ipv4"` to avoid consuming a public IPv4 address) — pure IPv6-only subnets work for ECS tasks but not for ALB nodes; put the ALB in the existing dual-stack subnets and only the ECS tasks in the IPv6-only ones.

- [2026-06-30] When introducing a new internal-only DNS hostname (e.g. for a CDN origin), it CANNOT reuse a name that's already a public alias to something else (e.g. `api.adopt-u.org` already aliases to the CloudFront distribution itself) - a single DNS name can only be one record type. Give the internal-only hostname its own distinct name (adopt-u uses `backend.adopt-u.org`); don't assume a semantically-fitting public name is free to reuse for internal plumbing without checking what it already points to.
- **The root Dockerfile had never actually built successfully** (confirmed 2026-06-30 by running `docker build` directly): it referenced a nonexistent `:backend:compileSass` Gradle task AND a nonexistent `:backend:shadowJar` task (Shadow plugin was never applied). Don't assume the Dockerfile works just because it's been merged/unchanged for a while — verify with an actual `docker build` before relying on or further editing it. See bug-067/068.
- **SCSS→CSS compilation is a manual dev-time step, not part of any build.** There is no Gradle Sass task and never was. Compiled `.css` files live committed in `backend/src/main/resources/static/css/` (see the existing `npx sass`/vendored-dart-sass workflow notes below) and are served from the jar's classpath via Ktor's `staticResources("/static", "static")`. The Dockerfile must not try to invoke a Sass build step.
- **backend uses `id("com.gradleup.shadow") version "9.4.3"`** (the maintained fork of the old `com.github.johnrengelman.shadow`, which is dead) to produce `backend/build/libs/*-all.jar`, the fat jar the Dockerfile packages. Keep the Shadow plugin version aligned with Gradle's major version (9.x plugin for Gradle 9.x).
- **`backend/build.gradle.kts`'s `kotlin { jvmToolchain(N) }` must match the JDK actually present in whatever image runs the build** (currently 25, matching `amazoncorretto:25-alpine-jdk` in the Dockerfile's builder stage). Toolchain auto-provisioning/download is not configured, so a mismatch fails the build immediately rather than degrading.
- **jlink-ing a custom runtime JRE: the JDK used as the `--module-path` source for `jlink` and the OS base image of the final runtime stage must share the same libc.** A JDK built against glibc (e.g. plain `amazoncorretto:25`) jlinked and then copied into a musl-based image (e.g. `alpine:*`) produces a `java` binary that fails to exec at all (`sh: java: not found` — a misleading error; it's actually a dynamic-linker/ABI failure, not a missing-file issue). Use the libc-matching JDK image (e.g. `amazoncorretto:25-alpine-jdk`) as the jlink source when the runtime stage is Alpine, and pin both stages to the *same* Alpine minor version to avoid musl ABI drift between versions. See bug-071.

- **kotlinx-serialization can't serialize a raw `Map<String, Any?>`/`call.respond(mapOf(...))` whose values mix multiple runtime types within one map.** Ktor's `KotlinxSerializationConverter` falls back to `guessSerializer()` (`io.ktor.serialization.kotlinx.SerializerLookup`) whenever a static type has no real serializer (e.g. generic `Any`/`Map<String, Any>`). That fallback requires every non-null value in the collection/map to resolve to the *same* `KSerializer` (`elementSerializer` does `distinctBy { it.descriptor.serialName }` and `error(...)`s if `size > 1`). A single-key map (`mapOf("blocked" to blocked)`) is fine; a map mixing e.g. Int + String + Long + Boolean across different keys throws `IllegalStateException` at serialize time, which Ktor's default pipeline turns into a 500 — even though the route code itself looks correct. Found this affecting `PhotographerService`'s request-map builders and `TemporalHomeRoutes`'s `/request` success payload (logged as bug-056). Fix is to respond with a proper `@Serializable` DTO instead of a raw mixed-type map, not to special-case Ktor.

- [2026-06-30] **Adding a required query param to a shared "list" endpoint can silently break internal consumers of that same endpoint.** `GET /api/pets` is used both by the public browse page (`index.js`) and by the rescuer/admin management page (`my-pets.js`, via `pets.filter(p => p.rescuerId === user.id)`). Making `country` mandatory + exact-match-filtering there (per the shelters/sterilization-locations pattern) would have hidden legacy pets with no country set from their own owner's management page. Fixed by adding a separate unfiltered `GET /api/pets/mine` (session-scoped, any status/country) for the management view, and keeping `GET /api/pets` strictly country-required for public search. Before making an existing repository/service method's parameter required, grep every route AND every static JS file calling that endpoint/method, not just the obvious one from the feature brief.
- [2026-06-30] `tokensave` MCP's index can point at an entirely different repo/worktree than the one you're actually working in (`tokensave_status` reports `worktree_mismatch` with the wrong `index_root`) — always check `tokensave_status` first; if it mismatches, fall back to plain Read/Grep instead of trusting search results from the wrong codebase.
- [2026-06-30] Ktor route trees resolve literal path segments before parameter segments at the same depth regardless of declaration order — confirmed by adding `get("/mine")` alongside an existing `get("/{id}")` under `/api/pets` (matching the pre-existing `get("/my-adoption-requests")` sibling). No need to register literal routes before parameterized ones.

- [2026-06-30] After merging a suspend-conversion branch (repo/service methods turned `suspend`) with another branch that added new test files against the pre-suspend synchronous API, expect the merge to succeed cleanly (git auto-merges non-overlapping lines) but leave `compileTestKotlin` broken with "Suspend function ... can only be called from a coroutine" errors — this is NOT a git conflict, it's a semantic API-shape mismatch invisible to `git merge`. Always re-run `:backend:compileTestKotlin` after this kind of merge before trusting a stale "all tests passing" claim from before the merge.
- [2026-06-30] `.wolf/buglog.json` (and other structured JSON files) can come out of a `git merge` with valid diff hunks per side but invalid combined JSON (e.g. two adjacent object entries merged without the `},\n    {` separator between them) — git's line-based merge doesn't understand JSON structure. After merging any `.json` file, validate with `python3 -c "import json; json.load(open(path))"` before trusting it, not just checking for `<<<<<<<` conflict markers (an auto-merge with zero conflict markers can still be syntactically broken).

- [2026-06-30] When a service-layer `require()` (e.g. new "country is required" validation) can be triggered via a public route for the first time, check whether that route already wraps the service call in `try { ... } catch (e: IllegalArgumentException) { call.respondError(...) }` (the `ShelterRoutes.kt`/`UserShelterRoutes.kt` convention) — `PetsRoutes.kt`'s `POST`/`PUT /api/pets` handlers did not, so adding required-country validation to `PetService.create()`/`.update()` would have 500'd instead of 400'd until the route handlers were updated to match the existing shelter-route error-handling pattern.

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->
- [2026-06-30] Runtime image switched from `amazoncorretto:25-alpine-jdk` (full JDK, ~190MB+ layer) to a custom `jlink`-built minimal JRE on plain `alpine`, derived per-build via `jdeps --print-module-deps` against the actual fat jar plus a small hardcoded safety-net module list (`jdk.crypto.ec`, `jdk.naming.dns`, `jdk.unsupported`, `java.naming` — TLS/DNS/Unsafe-reflection paths static `jdeps` analysis is known to miss for Netty/AWS-SDK-style libraries). Considered hand-picking a fixed module list instead of deriving via `jdeps`, rejected it as too fragile to dependency changes (silent breakage on a future library bump). Verified end-to-end by actually booting the built image against a real local Postgres container and confirming `Application started` + HTTP 200, not just a successful `docker build` — a build that completes doesn't prove a jlinked runtime can actually exec (see bug-071). Net result: ~124MB final image vs. the prior full-JDK Alpine base, faster ECR pull/cold start on Fargate.
- [2026-06-30] Declined to bake AppCDS (`-XX:ArchiveClassesAtExit`/`-XX:+AutoCreateSharedArchive`) into the image. Tried `-XX:+AutoCreateSharedArchive` as a runtime-only JAVA_OPTS flag; it only logged a CDS warning on every boot with zero benefit, because ECS Fargate tasks get a fresh ephemeral filesystem per launch — the archive file never survives to be reused on a second run. A real build-time-baked AppCDS archive would need a representative training run against live DB/AWS endpoints, which isn't safely scriptable inside the Dockerfile; skipped as not worth the fragility for this deployment model. Revisit only if ECS moves to long-lived/restart-in-place tasks.
- [2026-06-30] Country values switched from free-text `varchar` columns to an Exposed `enumerationByName` column backed by a new `Country` enum, after a Mexico search returned zero results due to an accent mismatch (`"Mexico"` dropdown value vs `"México"` stored in 2 shelter rows). Considered: (1) normalize the bad DB rows only, (2) make the filter comparison accent-insensitive, (3) make `Country` an enum and the single source of truth end-to-end. Chose (3), per explicit user direction, to eliminate the whole class of dropdown/DB drift rather than patch one symptom — affects 6 tables (shelters, sterilization locations, user shelters, user sterilization locations, temporal homes, photographers) that all shared the same free-text-country + exact-match-filter pattern.

- [2026-06-30] After fixing a serialized-DB-call bug by wrapping repositories in `withContext(Dispatchers.IO) { transaction { ... } }` (commit 95a5ce8), load-testing against the *actual* container resource cap (`--cpus=0.5 --memory=1024m`, matching ECS Fargate) showed this regressed throughput from 18.2 RPS to 0.1 RPS. `Dispatchers.IO` is elastic/unbounded (up to 64 threads) and assumes I/O-blocked threads don't cost real CPU — under a cgroup CPU cap that assumption is false, so 70-84 threads just thrash for the same half-core instead of adding parallelism. Fixed with a single shared bounded dispatcher (`Dispatchers.IO.limitedParallelism(4)`, `backend/src/main/kotlin/com/adoptu/adapters/db/DbDispatcher.kt`) reused across all 8 repositories. Lesson: an unbounded elastic dispatcher is not automatically "safe" just because it's the idiomatic choice for blocking I/O — always size dispatcher parallelism relative to the container's actual CPU allocation, and load-test fixes against real resource limits (not just correctness) before trusting them under production constraints.
- [2026-07-03] **Implemented a round of perf lessons from external DB/dispatcher-tuning advice, but treated the 2026-06-30 empirical result above as ground truth to preserve, not something to overwrite.** Added HikariCP pooling (`Database.connect(url,...)` had zero pooling — biggest single win available) and swapped `DbDispatcher`'s `Dispatchers.IO.limitedParallelism(4)` for a genuinely dedicated `Executors.newFixedThreadPool(n).asCoroutineDispatcher()`. New shared `PoolSizing.computeSize()` (`cores * 4` floored at 4) reproduces the *same validated 4* for the documented 1-core/0.5-vCPU case while scaling on bigger boxes — deliberately chosen so the swap can't regress the already-load-tested number, and used by both Hikari's `maximumPoolSize` and the dispatcher so they stay numerically coupled. **Declined two of the suggested optimizations after evaluating actual fit, rather than applying them by default:** (1) raw-JDBC bypass of Exposed's `Query`/`ResultRow` wrapping — `PetRepositoryImpl.getById` is a single-row PK lookup where wrapping overhead is negligible, and the one query that returns many rows (`getAll`'s listing) has variable filters (type/promoted/country/rescuerIds) that make it a poor "fixed-shape" candidate; forcing raw SQL there trades real correctness risk (hand-mapping 24 typed/nullable/enum columns) for marginal gain. (2) hand-rolled JSON encoding with a thread-local buffer for a "hot" DTO — no profiling data exists in this codebase to justify calling any endpoint hot in that sense (kotlinx.serialization here is already compile-time/non-reflective), so skipped rather than guessed. Also fixed a real N+1 in `PetRepositoryImpl.getAll`/`getAllUnfiltered` (already flagged as a known issue) by batch-fetching images for all returned pet IDs in one query instead of one nested `transaction{}` per pet, and audited every repository/service for blocking `transaction{}` calls made directly from suspend Ktor route handlers without a dispatcher wrap — found and fixed several in `PasswordService`/`EmailChangeService`/`MagicLinkService`/`WebAuthnService` (multiple methods were plain `fun`, not `suspend fun`, silently blocking whatever thread Ktor dispatched the request on) plus two stray `runBlocking` calls inside already-suspend route handlers in `PetsRoutes.kt`. Added `scripts/benchmark.sh` (Docker, `--cpus=0.5 --memory=1024m`, matching the exact profile that produced the 18.2 RPS number) so the new executor-based dispatcher can be re-validated against the same methodology before being trusted — this was NOT run end-to-end as part of this change (no live Postgres wired up in the execution sandbox); treat the dispatcher/pool-size numbers as unverified-in-production until that benchmark is actually run.
- [2026-06-30] Building Terraform/OpenTofu for an already-live AWS account (adopt-u prod): chose a hybrid brownfield strategy rather than either pure greenfield (would fail immediately - S3 bucket names, the RDS identifier, and CloudFront aliases are already taken in the account) or pure in-place mutation of the live single-replica ECS service (no redundancy, real risk of an outage mid-import). Stateful/identity-bound resources (S3 buckets, RDS instance, all 3 CloudFront distributions, the existing IAM role/policy names, most Route53 records) are written to match live config exactly and shipped with `tofu import` commands. Compute (ECS cluster/service/task def/security groups) is stood up as brand-new, freely-named resources that don't collide with anything, deployed in parallel alongside the still-running old service; the README documents a 4-step cutover (import -> stand up new compute -> manually re-point the `ecs.<domain>` record at the new task -> decommission the old hand-made resources) rather than one big-bang apply.
- [2026-06-30] First draft of this stack added an ALB + target group in front of the ECS service "to fix" the live deployment's fragile hardcoded-task-IP CloudFront origin. User rejected this forcefully and explicitly stated it had already been said before ("AGAIN!!"). Reverted: no load balancer of any kind. The fragility (DNS goes stale when the task restarts/redeploys) is solved instead by documenting a manual re-point step in the README, not by introducing new infrastructure the user didn't ask for. General lesson: don't "fix" something the user didn't flag as broken just because it looks fragile from the outside - ask, or at minimum match the live config exactly and call out the tradeoff in prose rather than silently architecting around it.
- [2026-07-01] `kotlin-js-store/` was gitignored, meaning `yarn.lock` (managed by the Kotlin/JS Gradle plugin) was never committed and could drift between machines, causing `Execution failed for task ':kotlinStoreYarnLock' ... Lock file was changed. Run the kotlinUpgradeYarnLock task`. If this error recurs after a legitimate dependency bump, rerun `kotlinUpgradeYarnLock` and commit the updated lock file rather than deleting/re-ignoring it. See bug-079.

- [2026-07-01] Full clean compile (`./gradlew clean :backend:compileKotlin :backend:compileTestKotlin :frontend:compileKotlinJs :frontend:compileTestKotlinJs`) surfaced 2 real compiler warnings not visible on incremental/UP-TO-DATE builds — `w:` lines only print on tasks that actually execute. Fixed: (1) `Sessions.kt` used deprecated `io.ktor.util.hex()`; replaced with stdlib `String.hexToByteArray()` (stable in Kotlin 2.4.0, no `@OptIn` needed) and dropped the now-unused `io.ktor.util.*` import. (2) `IndexPage.kt`'s `.then<Unit> { pets -> renderPets(pets); pets }` had an unused trailing `pets` expression since the lambda's declared return type is `Unit` — removed it. When asked to "fix compiler warnings," always force a clean recompile first; `--warning-mode all` only surfaces Gradle-level deprecations, not Kotlin compiler `w:` warnings, which need actual (re)compilation to print.
- [2026-07-03] **`DatabaseFactory.init()` can be called more than once in the same JVM** (`DatabaseFactoryInitIT` calls it once per `@Test`, each against a fresh Testcontainers database, `@TestInstance(PER_CLASS)`). After adding a HikariCP-backed `HikariDataSource` in `init()`, the first version didn't close the previous pool before building a new one — each call leaked a full pool's worth of live connections, and by the 4th/5th/7th call in the same test class the Postgres testcontainer hit its connection limit, failing with `HikariPool$PoolInitializationException` / `PSQLException` at pool-startup time. The old code (`Database.connect(url, driver, user, password)`, no pooling) never hit this because it opened connections lazily on first `transaction{}` use, not eagerly at construction. Fixed with `dataSource?.close()` at the top of `init()` before building the new one. **Any code that constructs a new `HikariDataSource` in a function that can re-run in the same JVM must close the previous instance first** — Hikari's eager connection-validation-at-construction makes leaks fail loudly (and fast) in a way lazy `DriverManager` connections never did.
- [2026-07-03] Actual production backend stack confirmed while implementing connection-pooling/dispatcher fixes: Ktor 3.5.1 + Netty engine, Exposed 1.3.0 (`org.jetbrains.exposed.v1.jdbc`), Koin DI, Gradle 9.6.1 (NOT Gradle 8 — a "jvmToolchain no-op under Gradle 8" concern doesn't apply here), `jvmToolchain(25)`. `tokensave`'s index for this project was pointing at an entirely different repo (`Bitakore`) — see 2026-06-30 entry above about `tokensave_status` mismatches; had to fall back to plain Grep/Read to map this codebase for real.
- [2026-07-03] **`scripts/benchmark.sh`'s original `--network host` approach silently fails on Docker Desktop** (macOS/Windows): `--network host` attaches to the Docker VM's network namespace, not the real host's, so a container can't reach a Postgres bound to the real host's `127.0.0.1`. `docker info` reporting `Operating System: Docker Desktop` is the tell. Fixed by publishing the port normally (`-p PORT:PORT`) and pointing the app's DB connection at `host.docker.internal` (`--add-host=host.docker.internal:host-gateway` makes this also work on native Linux Docker, where that hostname isn't defined by default). Verified with `docker run --rm --add-host=host.docker.internal:host-gateway alpine nc -zv host.docker.internal 5432` before trusting it — plain `/dev/tcp` checks in alpine's ash don't work (no bash), don't use that as a connectivity test.
- [2026-07-03] **Final dispatcher A/B, 6 rounds total (3 alternating pairs, 40s each, `--cpus=0.5 --memory=1024m`, `GET /api/pets?country=Mexico`), isolating only the dispatcher (same HikariCP pooling both times):** old `Dispatchers.IO.limitedParallelism(4)`: 7.03, 8.40, 10.35 RPS (mean 8.59, stdev 1.67). New dedicated `Executor`: 6.43, 6.66, 14.22 RPS (mean 9.10, stdev 4.43) — note round 3 *reverses* the direction seen in rounds 1-2, and both configs trend upward across the sequence (consistent with environmental drift — OS page cache / Postgres buffer cache warming, a competing worktree's live `:backend:run` process on the same box possibly easing off — not a per-config effect, since each round starts a fresh container/JVM with no JIT persistence between rounds). **Conclusion: no statistically confident winner; new dispatcher's mean is marginally higher but its variance is much larger.** Decision: keep the new dedicated-Executor dispatcher — it is not shown to be a regression, and it's structurally simpler/more predictable (a real fixed pool, not a bounded view over `Dispatchers.IO`'s shared elastic backing pool that other unrelated coroutine work in the app also draws from). Re-verify on a quieter box (ideally the real ECS target) before treating either number as authoritative.
- [2026-07-03] **The ~5-14 RPS measured here is not comparable to a separate "~300 RPS on the same 0.5 vCPU/1024MB ECS profile" figure from another project** — that number came from a GraalVM native-image build, not a plain JVM. This is an execution-model difference, not a tuning gap: native-image has no JIT warm-up (full speed from request 1) and a much smaller memory footprint, both of which matter enormously under a 1024MB/0.5-vCPU cap where a JVM's own startup/interpreter/JIT-compiler overhead eats into an already tiny budget. Confirmed via web research this session: Ktor's Netty engine (what adoptu uses) is NOT supported for GraalVM native-image — only the CIO engine is — so reaching that number here would require an engine swap plus resolving reflection/JNI compatibility for Koin (DI), WebAuthn4j, password4j (Argon2/JNI), and AWS SDK v2. Explicitly out of scope for this session — user confirmed a separate agent is handling the native-image track. Don't compare adoptu's plain-JVM throughput numbers to that 300 RPS figure again without accounting for this.
