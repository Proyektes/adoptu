## Key Learnings
- (2026-09-06) **A `@media` block placed EARLIER in a SCSS file than the unconditional base rule it's meant to override loses the cascade** even when the media query matches — same-specificity CSS resolves by source order regardless of media-query nesting, so `@media (max-width:600px){ .foo{display:flex} }` written near the top of `_layout.scss` was silently beaten by a plain `.foo{display:none}` rule declared further down the same file (bug-459). Confirmed live via `getComputedStyle(...).display` in a real browser tab at several widths, not just by reading the SCSS. **Convention going forward: responsive `@media` overrides for a selector must be declared AFTER that selector's own base rule in the same file** — the existing `@media (max-width:640px)`/`(max-width:400px)` blocks near the top of `_layout.scss` only "worked" because nothing unconditional after them happened to touch the same properties; don't copy their positioning as a pattern. Also confirmed the user's phrase "**better rescuers**" refers to the `topRescuers` i18n key (trophy icon, `#nav-urgent-leaderboard`) — its Spanish translation is literally "Mejores Rescatistas" ("Better/Best Rescuers"), not a distinct nav item; if a user names a nav label that doesn't literal-match any English string in `Shared.kt`, check `I18n.kt`'s Spanish dictionary for a translation before assuming the feature doesn't exist.
- (2026-09-06) **In this sandbox's Browser-pane tool, `computer{action:"left_click"}` targeting a `ref` from `read_page` does not reliably deliver the click to the page** (confirmed: same click, same ref, on a freshly-loaded tab, produced no state change — a `document.getElementById(...).click()` via `javascript_tool` immediately after did work) — this is on top of the already-known `screenshot` failure ("Browser pane is not displayed, so the page is not compositing frames"), suggesting the pane isn't actually rendering/receiving input in this environment. **When verifying click/toggle behavior here, drive the interaction with `javascript_tool` (`el.click()` or dispatch a real `MouseEvent`) and assert on `getComputedStyle`/`classList` state, rather than trusting `computer` clicks or screenshots.** Also reconfirmed the existing common.js-caching entry below: injecting a fresh `<script src=".../common.js?v=...">` to bypass Chromium's cache does NOT re-run the app's `DOMContentLoaded`-gated bootstrap (that event already fired), so a re-injected bundle's `initDropdowns()` etc. never runs automatically — call `window.AdoptuCommon.initDropdowns()` (module is exported as `window.Adoptu<Name>`, not a bare `window.Common`/`window.<PageName>`) by hand if testing this way, or just open a brand-new tab instead of reusing one.

- (2026-09-05) **AuthKit 1.3.0 (breaking) removed roles from authorization entirely — `AuthPrincipal.isSuperAdmin()` now checks `hasAllowedAction("superAdmin")`, not `roles.any { it.grantsAll() }`, and the JWT no longer carries a `roles` claim at all.** `requireRole`/`requireAnyRole` route guards were removed (use `requireAllowedAction(action)`); `hasRole`/`hasAnyRole`/`Role.grantsAll()` still exist on `AuthPrincipal`/`Role` but are now vestigial for gating — `hasRole()` internally is `isSuperAdmin() || roles.contains(role)`, and since `roles` is now always empty (nothing populates it from the token), only the `isSuperAdmin()` half ever fires. adoptu's ADMIN gate was 20 identical `!principal.hasRole(AdoptuRole.ADMIN)` checks across `UsersRoutes.kt`/`ShelterRoutes.kt`/`PetsRoutes.kt`/`SterilizationLocationRoutes.kt` — all replaced with `!principal.isSuperAdmin()` (unambiguous 1:1 swap since ADMIN was the only `grantsAll` role). **Critical backfill gotcha**: `AuthUser.allowedActions` is a new field defaulting to `emptySet()` — without populating it, every existing admin loses access the instant the gate switches to `isSuperAdmin()`, since nothing on `AuthUser`/the JWT ever set it. Fixed with **zero DB migration** by deriving it live in `AdoptuUserRepositoryAdapter.toAuthUser()`: `allowedActions = if (activeRoles.any { it.grantsAll() }) setOf(AuthPrincipal.SUPER_ADMIN_ACTION) else emptySet()` — this is the pattern AuthKit's own `Role.kt` doc comment recommends (`grantsAll` is now just "a host-side signal this role's assignment should also grant SUPER_ADMIN_ACTION"), and since it reads the already-persisted `user_active_roles` table at request time, no backfill script or new column was needed. adoptu's own `UserRole`/`activeRoles` business-role system (`UserActiveRoles` table, `UsersValidationService.validateRole`, `TemporalHomeService`'s RESCUER/ADMIN check) is a **completely separate, unaffected system** — it never touched AuthKit's `AuthPrincipal`/JWT roles claim, so none of it needed migrating.

- (2026-08-06) **Confirmed via `javap` bytecode inspection of Helidon 4.5.0's `SetCookie` class: passing `Duration.ZERO` to `.maxAge()` silently omits the `Max-Age` attribute entirely** (`if (maxAge != null && !isNegative && !isZero) append "Max-Age="` — zero is explicitly excluded, not rendered as `Max-Age=0`). AuthKit's `CookieAuthRoutes.kt` already knew this and works around it with `.expires(epoch)` instead. **adoptu's OLD `clearAuthCookies()`/Sessions.kt's `clearSession()` both used `.maxAge(Duration.ZERO)`** — meaning logout never actually sent a real deletion instruction for `adoptu_access_token`/`adoptu_refresh_token`/`user_session`; the cookie's value was overwritten to `""` but with no `Max-Age`/`Expires` it became a session cookie (cleared on browser close) instead of being purged immediately. Not a security hole (the token value itself is invalidated server-side and the cookie value is wiped), but a real hygiene gap. **Fixed for the AuthKit-issued cookies** as a natural side effect of switching to AuthKit's `clearAuthCookies()` (which uses the correct `.expires(epoch)` approach) and applied the same fix by hand to the `user_session` clear in `AuthRoutes.kt`. **`Sessions.kt`'s own `clearSession()` still has this exact bug and was NOT fixed** (out of scope for this session's task — flagged as a follow-up).

- **[2026-07-03] GraalVM native-image works for adoptu's Ktor/Exposed/AWS-SDK backend, but only via a specific config.** Full write-up: (1) Ktor's Netty engine has no native-image support — `EngineMain`/`embeddedServer` must use CIO instead. Added a second entry point, `ApplicationNative.kt` (`io.ktor.server.cio.EngineMain`), reusing the same `Application.module()`; the production `main()`/Netty path in `Application.kt` is untouched. (2) Logback-classic triggers a long chain of `UnsupportedFeatureException: ... was found in the image heap ... marked for initialization at image run time` errors, one class at a time (Logger → LoggerContext → Level → ConfigurationModel → TurboFilterList → AppenderModel → ... 15+ classes) — root cause: Netty ships its own `native-image.properties` marking many of its classes (`ChannelHandlerMask` etc.) build-time-initialized (for legitimate perf reasons unrelated to us — AWS SDK's `netty-nio-client` pulls Netty in transitively even though we don't use Netty's engine at runtime), and those classes hold static SLF4J logger fields that resolve to our real, fully-configured root `LoggerContext` (with the actual `ConsoleAppender[STDOUT]` attached) — so native-image tries to bake that whole live object graph into the image heap and rejects it until every reachable class is explicitly told `--initialize-at-build-time`. Trying `--initialize-at-run-time=io.netty.channel.ChannelHandlerMask` instead (to stop it being build-time-init'd in the first place) did NOT work — it silently reverted to the original error, so the class-list approach is the only path that worked. The full accumulated list lives in `backend/src/main/resources/META-INF/native-image/com.adoptu/adoptu-backend/native-image.properties`. (3) `--initialize-at-build-time=<package>` is NOT recursive in this GraalVM version (25/native-build-tools 1.1.3) — `ch.qos.logback` alone silently reverts to the very first error; you must list the exact package containing the class (`ch.qos.logback.classic`) or the fully-qualified class name. A multi-line `Args = ... \` continuation in `native-image.properties` also silently breaks (reverts to first error) — keep `Args` on one line. (4) **Building via plain `native-image -cp <shadowJar>` vs. Gradle's `:backend:nativeCompile` (plugin-managed, non-shadowed classpath) are NOT equivalent** — the same `native-image.properties` that fully worked under Gradle's nativeCompile still hit one extra class (`SimpleTimeBasedGuard`) under a direct shadowJar-based invocation. Shadow's uber-jar merging apparently changes which library's conflicting `META-INF/native-image/**` directive wins for overlapping classes. **The Gradle path (`org.graalvm.buildtools.native` + `graalvmNative{}` in `backend/build.gradle.kts`) is the validated, supported way to build this image — not raw `native-image -cp shadowJar.jar`.** (5) A single `./gradlew :backend:jar :backend:nativeCompile --no-daemon` invocation inside the `ghcr.io/graalvm/native-image-community:25` Docker image OOM-kills (exit 137) in a 7-8GB container — the Kotlin-compile JVM heap and native-image's own ~80%-of-container heap claim overlap. Fix: run `:backend:jar` and `:backend:nativeCompile` as **two separate** `--no-daemon` invocations (see `scripts/build-native-image.sh`) so the first JVM fully exits before native-image starts. (6) `graalvmNative { metadataRepository { enabled.set(true) } }` pulls community-vetted reflection/resource config automatically for known libraries (logback-classic, AWS SDK, etc.) — worth keeping even though it did not by itself resolve the class-initialization chain above (that's a different concern, orthogonal to reflection config). (7) End-to-end verified: agent-traced `reachability-metadata.json` (via `-agentlib:native-image-agent`, hitting real routes against live Postgres) + the class-init list above produces a working 134MB native binary that serves every route tested (home, static assets, all page routes, admin, `/api/auth/login-with-password` including the full CryptoService/Argon2 path) identically to the JVM build, with ~1.3s startup (vs ~4s for the jlinked JVM). See [[graalvm-native-image-decision]].

- **kotlinx-serialization can't serialize a raw `Map<String, Any?>`/`call.respond(mapOf(...))` whose values mix multiple runtime types within one map.** Ktor's `KotlinxSerializationConverter` falls back to `guessSerializer()` (`io.ktor.serialization.kotlinx.SerializerLookup`) whenever a static type has no real serializer (e.g. generic `Any`/`Map<String, Any>`). A single-key map (`mapOf("blocked" to blocked)`) is fine; a map mixing e.g. Int + String + Long + Boolean across different keys throws `IllegalStateException` at serialize time, which Ktor's default pipeline turns into a 500 — even though the route code itself looks correct.
