## Key Learnings
- [2026-07-03] The Profile page (`/profile`) has TWO parallel, non-identical implementations of the same features, same pattern already known for i18n (see below): a hand-written `profile.js`/`api.js` pair (dead code — no page ever loads `profile.js`) and a Kotlin/JS `ProfilePageModule`/`ApiClientModule` (compiled into `common.js`, actually live). When a profile feature (password/email/name/country change) appears broken, check `ProfilePageModule` in `frontend/src/jsMain/kotlin/com/adoptu/frontend/pages/ProfilePage.kt` and `ApiClientModule` in `frontend/src/jsMain/kotlin/com/adoptu/frontend/ApiClient.kt` — NOT `backend/src/main/resources/static/js/profile.js`, which looks plausible but never executes.
- [2026-07-03] `GET /api/auth/me` (`AuthMeResponse`, built in `AuthRoutes.kt`'s `userAuthenticationSuccess()`) must read `displayName`/`email`/`country` from the freshly-fetched `UserDto` (`user.xxx`), not from `SessionUser` (`session.xxx`) — the session object is a snapshot taken at login time and never refreshes, so any field sourced from it will silently show stale data on every page that calls `api.me()` until the next login/logout cycle. `language`/`activeRoles`/ban fields already correctly used the fresh DTO; only `displayName`/`email` had this bug, and `country` was missing from the response entirely.
- [2026-07-03] Kotlin's `EnumerationNameColumnType.valueFromDB` (Exposed's `enumerationByName` column type) throws `"$value can't be associated with any from enum ${klass.qualifiedName}"` when a DB string doesn't match any enum `.name`. If you see this exact wording (not Kotlin's own `Enum.valueOf` message, which is `"No enum constant ..."`), the mismatch is in raw SQL-seeded data vs. an Exposed `enumerationByName` column, not a Kotlin service-layer bug — check whether the seed SQL used the enum's `.name` (e.g. `MEXICO`) vs. its `displayName` (e.g. `México`). `animal_shelters`/`sterilization_locations` get their rows via app-level sync (correct format); `photographers`/`temporal_homes`/`user_shelters`/`user_sterilization_locations` are seeded directly via raw INSERT in `scripts/test_data.sql` and are the ones at risk of this.
- [2026-07-03] `./gradlew :backend:run` only recopies `backend/src/main/resources/**` into `backend/build/resources/main/**` (via `processResources`) at task start — editing ANY backend resource file (static JS/CSS, `application.conf`, etc.) or Kotlin source while a `:backend:run` process is already running has zero effect until you kill it and start a new `:backend:run`. There is no hot-reload. Same applies to `frontend/src/jsMain/kotlin/**` changes needing `:frontend:jsBrowserProductionWebpack` before the backend serves the updated `common.js` — and the backend must ALSO be restarted after that, since `common.js` is a static resource subject to the same one-time-copy-at-startup behavior.
- [2026-07-03] When a Playwright test in this suite performs 2+ real logins (`loginWithPassword`, ~9s each for argon2 hashing) plus an intentionally-failed login (which burns `loginWithPassword`'s internal 20s `waitForURL` timeout waiting for a redirect that never comes), the sequential time easily exceeds Playwright's default 30s per-test timeout even though every step is individually correct. Add `test.setTimeout(60000)` at the top of that specific test rather than treating the failure as a product bug.

- **[2026-07-03] GraalVM native-image works for adoptu's Ktor/Exposed/AWS-SDK backend, but only via a specific config.** Full write-up: (1) Ktor's Netty engine has no native-image support — `EngineMain`/`embeddedServer` must use CIO instead. Added a second entry point, `ApplicationNative.kt` (`io.ktor.server.cio.EngineMain`), reusing the same `Application.module()`; the production `main()`/Netty path in `Application.kt` is untouched. (2) Logback-classic triggers a long chain of `UnsupportedFeatureException: ... was found in the image heap ... marked for initialization at image run time` errors, one class at a time (Logger → LoggerContext → Level → ConfigurationModel → TurboFilterList → AppenderModel → ... 15+ classes) — root cause: Netty ships its own `native-image.properties` marking many of its classes (`ChannelHandlerMask` etc.) build-time-initialized (for legitimate perf reasons unrelated to us — AWS SDK's `netty-nio-client` pulls Netty in transitively even though we don't use Netty's engine at runtime), and those classes hold static SLF4J logger fields that resolve to our real, fully-configured root `LoggerContext` (with the actual `ConsoleAppender[STDOUT]` attached) — so native-image tries to bake that whole live object graph into the image heap and rejects it until every reachable class is explicitly told `--initialize-at-build-time`. Trying `--initialize-at-run-time=io.netty.channel.ChannelHandlerMask` instead (to stop it being build-time-init'd in the first place) did NOT work — it silently reverted to the original error, so the class-list approach is the only path that worked. The full accumulated list lives in `backend/src/main/resources/META-INF/native-image/com.adoptu/adoptu-backend/native-image.properties`. (3) `--initialize-at-build-time=<package>` is NOT recursive in this GraalVM version (25/native-build-tools 1.1.3) — `ch.qos.logback` alone silently reverts to the very first error; you must list the exact package containing the class (`ch.qos.logback.classic`) or the fully-qualified class name. A multi-line `Args = ... \` continuation in `native-image.properties` also silently breaks (reverts to first error) — keep `Args` on one line. (4) **Building via plain `native-image -cp <shadowJar>` vs. Gradle's `:backend:nativeCompile` (plugin-managed, non-shadowed classpath) are NOT equivalent** — the same `native-image.properties` that fully worked under Gradle's nativeCompile still hit one extra class (`SimpleTimeBasedGuard`) under a direct shadowJar-based invocation. Shadow's uber-jar merging apparently changes which library's conflicting `META-INF/native-image/**` directive wins for overlapping classes. **The Gradle path (`org.graalvm.buildtools.native` + `graalvmNative{}` in `backend/build.gradle.kts`) is the validated, supported way to build this image — not raw `native-image -cp shadowJar.jar`.** (5) A single `./gradlew :backend:jar :backend:nativeCompile --no-daemon` invocation inside the `ghcr.io/graalvm/native-image-community:25` Docker image OOM-kills (exit 137) in a 7-8GB container — the Kotlin-compile JVM heap and native-image's own ~80%-of-container heap claim overlap. Fix: run `:backend:jar` and `:backend:nativeCompile` as **two separate** `--no-daemon` invocations (see `scripts/build-native-image.sh`) so the first JVM fully exits before native-image starts. (6) `graalvmNative { metadataRepository { enabled.set(true) } }` pulls community-vetted reflection/resource config automatically for known libraries (logback-classic, AWS SDK, etc.) — worth keeping even though it did not by itself resolve the class-initialization chain above (that's a different concern, orthogonal to reflection config). (7) End-to-end verified: agent-traced `reachability-metadata.json` (via `-agentlib:native-image-agent`, hitting real routes against live Postgres) + the class-init list above produces a working 134MB native binary that serves every route tested (home, static assets, all page routes, admin, `/api/auth/login-with-password` including the full CryptoService/Argon2 path) identically to the JVM build, with ~1.3s startup (vs ~4s for the jlinked JVM). See [[graalvm-native-image-decision]].

- **`Country` (backend/src/main/kotlin/com/adoptu/common/Country.kt) is the single source of truth for country values.** The dropdown (`Shared.kt: countrySelect()`), DB storage (`Models.kt` columns use `enumerationByName("country", 100, Country::class)`), and validation (every repository touching a `country` column calls `Country.fromDisplayName()` before reading/writing) all derive from this enum. The DB subnet group must support `DUAL` (check `aws rds describe-db-subnet-groups`) before this is possible; intra-VPC routing then handles it with no NAT/IGW involved either way.
- **For "no NAT" + IPv6-only ECS Fargate**: a VPC with an Amazon-provided IPv6 `/56` (the default for newer default VPCs) is "public" IPv6 — the VPC's main route table already has `::/0 -> igw`, so IPv6-only subnets get direct internet egress through the regular Internet Gateway with zero extra routing config (no NAT Gateway, no Egress-Only IGW needed). ALBs, however, still require a subnet with an IPv4 CIDR present (even when using `ip_address_type = "dualstack-without-public-ipv4"` to avoid consuming a public IPv4 address) — pure IPv6-only subnets work for ECS tasks but not for ALB nodes; put the ALB in the existing dual-stack subnets and only the ECS tasks in the IPv6-only ones.

- **`backend/build.gradle.kts`'s `kotlin { jvmToolchain(N) }` must match the JDK actually present in whatever image runs the build** (currently 25, matching `amazoncorretto:25-alpine-jdk` in the Dockerfile's builder stage). - **jlink-ing a custom runtime JRE: the JDK used as the `--module-path` source for `jlink` and the OS base image of the final runtime stage must share the same libc.** A JDK built against glibc (e.g. plain `amazoncorretto:25`) jlinked and then copied into a musl-based image (e.g. `alpine:*`) produces a `java` binary that fails to exec at all (`sh: java: not found` — a misleading error; it's actually a dynamic-linker/ABI failure, not a missing-file issue). Use the libc-matching JDK image (e.g. `amazoncorretto:25-alpine-jdk`) as the jlink source when the runtime stage is Alpine, and pin both stages to the *same* Alpine minor version to avoid musl ABI drift between versions. See bug-071.

- **kotlinx-serialization can't serialize a raw `Map<String, Any?>`/`call.respond(mapOf(...))` whose values mix multiple runtime types within one map.** Ktor's `KotlinxSerializationConverter` falls back to `guessSerializer()` (`io.ktor.serialization.kotlinx.SerializerLookup`) whenever a static type has no real serializer (e.g. generic `Any`/`Map<String, Any>`). That fallback requires every non-null value in the collection/map to resolve to the *same* `KSerializer` (`elementSerializer` does `distinctBy { it.descriptor.serialName }` and `error(...)`s if `size > 1`). A single-key map (`mapOf("blocked" to blocked)`) is fine; a map mixing e.g. Int + String + Long + Boolean across different keys throws `IllegalStateException` at serialize time, which Ktor's default pipeline turns into a 500 — even though the route code itself looks correct. Found this affecting `PhotographerService`'s request-map builders and `TemporalHomeRoutes`'s `/request` success payload (logged as bug-056). Fix is to respond with a proper `@Serializable` DTO instead of a raw mixed-type map, not to special-case Ktor.

- [2026-06-30] Ktor route trees resolve literal path segments before parameter segments at the same depth regardless of declaration order — confirmed by adding `get("/mine")` alongside an existing `get("/{id}")` under `/api/pets` (matching the pre-existing `get("/my-adoption-requests")` sibling). - [2026-07-03] **This does NOT carry over to Helidon Níma** (this project migrated its backend from Ktor to Helidon 4.5.0 - see [[helidon-migration-decision]]). Confirmed via `javap` on `io.helidon.webserver.http.RouteCrawler` that Helidon matches routes with a linear iterator over a registration-ordered `List<HttpRouteBase>` (first-registered-first-tried), not a specificity-sorted tree. A literal route registered AFTER a conflicting `{param}` route at the same path depth is silently unreachable. When porting/adding Helidon routes, always register literal siblings (e.g. `/api/pets/mine`) BEFORE any `{param}` route at the same depth (e.g. `/api/pets/{id}`) in the same `fun HttpRules.xxxRoutes()` function - verified empirically end-to-end (curl against a running server) after `PetsRoutes.kt`'s port initially got this backwards.
- [2026-07-03] **Full Ktor→Helidon Níma + Jackson backend migration, key gotchas** (see [[helidon-migration-decision]] for the full writeup and file inventory): (1) Helidon's Gradle artifact for static file serving is `io.helidon.webserver:helidon-webserver-static-content` (hyphenated "static-content"), NOT "staticcontent" - guessing the latter fails dependency resolution with no near-match suggestion. (2) `JacksonSupport.create(objectMapper)` and `MultiPartSupport.create(...)` both exist, but `MultiPartSupport` has no zero-arg `create()` - it needs a `io.helidon.common.config.Config` argument; `Config.empty()` works fine when there's nothing to configure. (3) Multipart parts: `io.helidon.http.media.multipart.MultiPart` implements `Iterator<ReadablePart>` (`hasNext()`/`next()`), and each `ReadablePart` has `.name()`, `.fileName(): Optional<String>`, `.contentType(): HttpMediaType`, `.inputStream()` (inherited from `ReadableEntity`) - confirmed via bytecode inspection of the actual jar, not docs (Maven Central lets you `curl` an artifact directly by exact coordinate+version to `javap` it when Gradle's own cache doesn't have it yet, without needing a full build). (4) `ServerRequest.content(): ReadableEntity` throws when you call `.as(String::class.java)` on a zero-length/absent body - always check `.hasEntity()` first if the body can legitimately be empty (see bug-037). (5) Koin's plain `KoinComponent`/`inject()` (koin-core, not koin-ktor) works identically outside Ktor - `object Deps : KoinComponent` + `by Deps.inject<T>()` is a drop-in replacement for `org.koin.ktor.ext.inject`. (6) Helidon's legacy `StaticContentService.builder("static").build()` + `routing.register("/static", service)` is deprecated since 4.1.5 but still fully functional - the "modern" `StaticContentFeature`/`ClasspathHandlerConfig` replacement wasn't worth the extra research time for an unchanged behavioral outcome. (7) Coroutines/suspend service and repository code did NOT need to change - Helidon Níma Handlers run on one virtual thread per request (not a coroutine dispatcher), so wrapping the suspend-calling portion of each handler in `kotlinx.coroutines.runBlocking { }` is a correct, low-risk bridge that let ~10,000 lines of existing suspend-based services/repositories/DB-dispatcher code (including the recently-tuned HikariCP pooling work) carry over completely unchanged.
